# 足球计算器（Football Calculator）MVP 设计规格

日期：2026-05-08  
状态：草案（待评审）  

## 目标与范围

### 产品目标（MVP）
- 用户上传竞彩足球实体票/截图（可多张），系统通过 OCR 识别出票面信息（含票面 SP/赔率）。
- 用户对识别结果进行手动校对后，系统根据**票面 SP**与**实际赛果**判断是否中奖，并计算**预计中奖金额**（覆盖常见串关与倍投）。
- 同时提供基础的足球资讯能力：赛程/赛果列表 + 赔率/趋势展示 + 简单分析卡片（不做重资讯站）。

### 明确选择（来自确认结果）
- **优先级**：先做“彩票识别与中奖计算”，资讯先做轻量但可用。
- **首版玩法**：中国体彩竞彩足球 **胜平负（SPF）** / **让球胜平负（RQSPF）**。
- **计算复杂度**：支持常见串关（如 2串1、3串1…）+ 倍投；奖金按**票面打印 SP**计算。
- **体验**：允许用户校对/修改识别结果后再计算。
- **上传形态**：拍照 + 截图都支持；允许多图合并同一张票。
- **账号**：首版匿名；后续可加账号体系并绑定历史记录。
- **技术路线**：R1（传统 OCR + 规则解析）优先。

### 非目标（MVP 不做/不保证）
- 不追求一次性全自动准确识别；以“可校对”保证最终计算正确。
- 暂不覆盖：比分/总进球/半全场、混合过关、胆拖、特殊退款/取消/中止/延期等全量边界（见“风险与扩展”）。
- 不做重资讯（新闻、专题、球队/球员全量数据、复杂推送等）。

## 用户体验与页面结构

### 核心用户旅程
1) 上传拍照/截图（可多张）  
2) OCR + 解析生成结构化票据（关键字段缺失时标红）  
3) 用户校对（补全/修正：玩法、选项、SP、倍数、串关、比赛匹配）  
4) 拉取赛果并计算预计奖金  
5) 输出报告（命中明细、未命中原因、预计奖金与组合明细、可分享）

### 页面（Web）
- `首页`：入口（上传），以及“近期赛果/热门比赛”轻量组件
- `上传页`：多图上传、裁剪/旋转、清晰度提示
- `识别校对页`：表格/卡片按比赛逐行展示；关键字段高亮；支持增删改
- `计算结果页`：总预计奖金、命中/未命中明细、按串关组合的奖金明细、复算入口
- `赛程/赛果页`：列表 + 比分/时间/队伍 + 赔率/趋势组件 + 简单分析卡片
- `我的票（匿名）`：使用临时 token 保存的历史记录列表（可复制分享链接）

## 架构与模块边界

### 客户端（Web）
- 图片采集与预处理：裁剪/旋转/压缩、清晰度提示
- 识别结果展示与校对：把“机器建议值”与“用户最终值”区分并可追踪
- 计算触发与报告展示：展示“缺失字段/无法匹配赛果”的阻断原因

### 服务端（API）
- `OCRService`
  - 输入：图片（多张）
  - 输出：文本块/文本行（含位置、置信度）
- `TicketParser`
  - 输入：OCR 输出（文本 + 位置信息）
  - 输出：统一 `Ticket` 结构（可版本化）
- `ResultsProvider`
  - 输入：比赛标识（由 `matchKey` 解析/匹配得出）
  - 输出：实际赛果；（可选）赔率趋势用于资讯展示
- `PayoutEngine`
  - 输入：`Ticket`（用户校对后的最终结构）+ `Results`
  - 输出：`PayoutReport`
- `AnonymousStore`
  - 基于临时 token 保存 `TicketDraft` 与 `PayoutReport`
  - 为后续账号体系预留“绑定/迁移”能力

## 数据模型（统一结构）

> 原则：前后端都以同一份结构传递与校验；“可校对”意味着任何字段都必须能被用户编辑并重新校验。

### Ticket（票据）
- `ticketType`: `"jc-football"`
- `playType`: `"SPF"` | `"RQSPF"`（MVP 仅这两类）
- `multiplier`: number（倍数/倍投）
- `passTypes`: string[]（例如：`["2x1"]`、`["3x1","2x1"]`；具体可扩展）
- `legs`: Leg[]

### Leg（单场/单选择）
- `matchKey`: string（用于匹配比赛；由 OCR 提取 + 规则归一化；允许用户修正）
  - 建议包含：比赛日期/时间、联赛、主队、客队（从票面文本尽量抽）
- `selection`: `"胜"` | `"平"` | `"负"`（SPF）或 `"让胜"` | `"让平"` | `"让负"`（RQSPF）
- `handicap`: number | null（RQSPF 必填；从票面识别，允许用户修正）
- `sp`: number（**票面打印 SP/赔率**；必须可编辑）

### TicketDraft（识别草稿）
- `ticket`: Ticket（可能缺字段）
- `confidence`: 结构化置信度（字段级别：`spConfidence`、`matchConfidence` 等）
- `warnings`: string[]（缺字段、低置信度、冲突合并等）
- `sourceImages`: 图片引用列表（用于回溯）

### Results（赛果）
- `matches`: { matchId, finalScore, outcomeSPF, outcomeRQSPF, ... }[]

### PayoutReport（计算报告）
- `status`: `"won"` | `"lost"` | `"pending"` | `"partial"`（视边界情况扩展）
- `totalPayout`: number（预计总奖金）
- `details`:
  - `legResults`: 每个 leg 是否命中、命中依据、对应赛果
  - `comboBreakdown`: 过关组合明细（组合、乘积 SP、倍数、奖金）
- `unmatchedLegs`: 无法匹配赛果的 leg 列表（阻断计算或给出部分结果）

## 识别链路（R1：OCR + 规则解析）

### OCR 输出形态
- 输出：`[{ text, bbox, confidence, lineGroupId? }]`
- 需要支持中文、数字、小数点、`×`、`串` 等符号

### 解析策略（逐层）
1) **区域/行分组**
   - 倍数区、串关区、比赛列表区
   - 以空间位置 + 关键词引导（如“倍投/倍”、“串”）
2) **字段抽取**
   - `multiplier`：识别 `倍`/`倍投`/`×N`
   - `passTypes`：识别 `2串1/3串1...`，归一化为 `2x1/3x1...`
   - 比赛行：抽取对阵、玩法（SPF/RQSPF）、让球、选项、SP
3) **结构化校验与标注**
   - 缺失关键字段（`selection/sp/passTypes/multiplier/handicap`）→ 标红并加入 `warnings`
   - 低置信度 → 字段级高亮（引导用户重点校对）
4) **多图合并**
   - 同票多图：按“比赛行相似度 + 串关/倍数一致性”合并
   - 冲突（如同一场出现不同 SP）→ 进入“需要用户选择”的冲突列表

### 校对机制
- 用户校对后形成 **Final Ticket**（所有必填字段齐全且通过校验）
- 所有修改触发重新校验；未通过不允许进入计算

## 赛果与资讯数据

### MVP 需求
- 计算必须依赖实际赛果（比分/胜平负结果/让球胜平负结果）。
- 资讯页展示赔率/趋势与简单分析卡片，但**不用于奖金计算**（奖金仅用票面 SP）。

### 数据源策略（先设计为可替换）
- 抽象 `ResultsProvider` 接口，支持后续替换不同第三方数据源或自建抓取。
- MVP 可先用单一数据源满足：赛程、赛果、基础赔率/趋势（若不可得则降级为无趋势）。

## 奖金计算（按票面 SP）

### 输入
用户校对完成的 `Ticket` + 可匹配的 `Results`

### 计算逻辑（MVP）
1) 判断每个 `leg` 是否命中（SPF/RQSPF）
2) 按 `passTypes` 生成过关组合（常见串关）
3) 每个组合奖金（MVP 公式，先按“每注 2 元”与票面 SP 乘积估算）：
   - 组合奖金 \(= (\prod sp) \times 2 \times multiplier\)
4) 汇总 `totalPayout`，输出组合明细与命中明细

### 关键边界（需在实现阶段细化/显式声明）
- 舍入规则、单注上限、取消/推迟/中止、让球变更、特殊结算等。
- MVP：先覆盖“正常完赛、赛果明确”的主路径；其余情况在报告中给出“无法精确结算/需人工确认”的状态。

## 接口草案（示意）

- `POST /api/tickets/recognize`
  - 入参：images[]
  - 出参：TicketDraft（含 warnings/confidence）

- `POST /api/tickets/validate`
  - 入参：Ticket（用户校对后的结构）
  - 出参：校验结果（errors/warnings）

- `POST /api/tickets/calculate`
  - 入参：Ticket
  - 出参：PayoutReport

- `GET /api/matches?date=...`
  - 出参：赛程/赛果列表（资讯页用）

## 存储与匿名策略

### 匿名 MVP
- 生成 `anonToken`（本地存储 + 可分享 URL）
- 服务端按 `anonToken` 保存：最近 N 条票据与报告
- 用户清理缓存/换设备将失去历史（MVP 可接受）

### 后续账号扩展（不推倒重来）
- 引入 `User` 与 `UserSessions`
- 将 `anonToken` 下数据迁移/绑定到 `userId`

## 风险与对策

- **OCR 质量波动**：拍照模糊、反光、裁剪不完整  
  - 对策：前端清晰度提示 + 强制校对关键字段 + 置信度高亮

- **票面模板差异**：不同地区/批次/打印格式略有差异  
  - 对策：解析器版本化；对识别失败样本做回放与迭代；保留原图回溯

- **赛果匹配失败**：OCR 拿不到完整对阵/时间  
  - 对策：提供“手动选择比赛”的 UI；允许先算部分/或阻断并提示

## 里程碑（建议）
- M1：上传 + OCR 输出可视化 + 结构化草稿（不含计算）
- M2：校对页 + 校验规则完善
- M3：赛果对接 + SPF/RQSPF 命中判断
- M4：常见串关 + 倍投奖金计算 + 报告页
- M5：资讯页（赛程/赛果 + 赔率/趋势 + 简单分析卡片）
